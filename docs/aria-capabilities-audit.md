# Aria Capabilities Audit — Read-only baseline

**Status:** Baseline audit complete. The approved backend temporary-session foundation slice is implemented and tested; later capability slices still require review and approval. No frontend changes or real Gemini calls were made.

## Scope, worktree, and evidence standard

The requested scope is the longer-term direction: useful conversation context, current-order lookup and natural references (e.g. “cancel my vitamin C”), ambiguity handling and confirmation, plus accounts, product inventory, carts, and order creation. Scope is based on the project’s functional requirements, tool list, mock orders, backend source/tests, and existing frontend/WebSocket contracts.

Worktree inspection: branch `feature/make-aria-smarter`; pre-existing dirty changes at audit start were `frontend/package.json`, `frontend/package-lock.json`, untracked `.agents/`, `.opencode/agents/backend.md`, `frontend/tests/e2e/`, `opencode.json`, root `package.json`, root `package-lock.json`, and `skills-lock.json`. These were left untouched. Nothing was staged or committed; in particular this audit did not commit to `main`. No existing `docs/aria-capabilities-audit.md` was present at audit start.

“Verified” below means directly supported by repository source/document/test text, not verified against a live provider. Provider/model tool selection, transcription accuracy, intent or reference resolution, and actual naturalness are explicitly unverified absent a real provider run. All cited paths and line numbers refer to the inspected worktree at audit time.

## Requirements and project contracts

- Functional requirements call for conversational context (FR-03), order lookup and Python-owned policy (FR-06/07, FR-15/16), and explicitly put accounts/login/order ownership and production DB out of scope in the initial milestone (`docs/aura_skincare_functional_requirements.md:20-38, 40-72, 74-93, 137-149`). It says missing IDs should be requested (`:66-72`); natural item/name resolution is a future enhancement, not an existing requirement.
- The callable tool list names seven tools; only five order/policy tools have a schema there, while cart/order-creation behavior is explicitly an implementation-only demo contract (`docs/aura_tool_call_list.md:3-35`).
- Three static fixture orders are documented (`docs/mock-orders.md:9-59`), with no real customer data (`:7`). Backend JSON matches the three fixtures (`backend/app/data/orders.json:1-32`).
- WebSocket contract defines one call per connection, fresh session-local OrderService, audio/control messages, transcript/tool/result/summary events, and no identity or account credential in the handshake (`docs/ws-event-contract.md:8-28, 30-71, 82-98`).
- Frontend contract says browser calls FastAPI only and backend owns session, tools, order/session state, policy, prices and confirmation; frontend renders backend results (`docs/frontend-call-integration.md:32-43`). Natural item references / account state are not supplied as a separate frontend mechanism.

## Current capabilities and data flow (source-verified)

### Session and conversation context

`/ws/call` checks an optional Origin, accepts a socket, allocates local transcript, confirmation map, user-turn counter, and one `OrderService`; it applies concurrency, idle and duration limits (`backend/app/main.py:52-90, 282-291`). `start_call` creates a Gemini adapter and connects; per-session provider event consumption handles transcription, output, audio, and tool calls (`backend/app/main.py:117-228, 368-396`). The adapter configures system prompt, declared tools, and transcription (`backend/app/live/session.py:42-63`). The prompt describes Aria’s behavior and policies (`backend/app/live/prompt.py:3-32`).

The live provider itself maintains conversational interaction during the connection, while the backend retains only a transcript list and action/tool state scoped to that WebSocket; no durable conversation memory, user profile, or cross-call continuity is implemented (`backend/app/main.py:75-79, 177-204, 281-282`). Summary is generated from backend transcript and tool records at graceful finish, not model memory (`backend/app/main.py:97-111`; `backend/app/live/summary.py:26-67`). Disconnect cleanup closes the session and cancels tasks; it does not guarantee summary (`backend/app/main.py:401-452`; `docs/ws-event-contract.md:122-131`). The WS contract expressly defines one connection as one session (`docs/ws-event-contract.md:8-16`).

**Risk:** transcript and tool history have no explicit retention policy beyond connection lifetime; turns may contain personal data. Account context must not be added to model-persistent/provider state or reused across calls without an explicit authenticated identity, scope and expiry design. In-memory maps are not durable or multi-worker state.

### Customer and order identity / natural reference

There is no account authentication, customer identity, ownership relation, or authorization check. Mock orders contain customer names but the lookup API accepts an order ID and returns the entire order (`backend/app/data/orders.json:1-32`; `backend/app/domain/orders.py:30-64`; requirements mark accounts/ownership out of scope at `docs/aura_skincare_functional_requirements.md:137-149`). Thus current order identity is effectively possession/knowledge of a globally guessable `ORD-###`, not proof of the caller’s right to see it. Three predictable fixture IDs are especially unsuitable as an authorization model.

Tool schemas require `order_id` for lookup, cancellation and eligibility (`backend/app/tools/registry.py:16, 34-44`). The prompt explicitly says never guess or infer IDs, and ask to repeat unclear/missing IDs (`backend/app/live/prompt.py:8-10`); requirements similarly prescribe asking for missing ID (`docs/aura_skincare_functional_requirements.md:68-71`). No backend resolver maps “my vitamin C” to one of the caller’s orders, nor lists current orders. `OrderService._current_order` validates ID shape and finds a seed/new order, but does not resolve names or ownership (`backend/app/domain/orders.py:30-42`).

**Implication:** natural reference needs a trusted resolver over authorized customer orders, not prompt-only inference. A product name may identify multiple orders, and multiple customers can have similarly named items; missing, stale, partial, or ambiguous referents must trigger clarification. Do not leak whether another customer’s order exists. For anonymous demo mode, any natural resolution must remain explicitly session/demo-scoped and not be represented as account-authenticated.

### Tool selection, validation, and backend trust boundary

Seven tools are allowlisted in a fixed registry; unknown names and malformed/extra args are rejected, and tool result is returned to Gemini keyed by provider call ID (`backend/app/tools/registry.py:34-49, 53-120, 138-159`; `backend/app/main.py:207-228`). The backend supplies tool declarations and system instructions (`backend/app/live/session.py:34-39, 52-57`). IDs are normalized and validated, cart arguments restrict quantity/product/payment fields, and customer-declared return/damage facts are typed inputs (`registry.py:67-120`). The backend owns order status, totals, policy and catalog prices; model-supplied status/price/eligibility fields are rejected (`registry.py:64-66`; `backend/app/domain/orders.py:44-64, 139-170`; tests `backend/tests/test_tool_registry.py:18-28, 64-71`).

Tool invocation and natural language understanding are separate: the registry validates structured arguments but does not establish that the caller asked for an operation, owns the order, or supplied correct customer-declared facts. Model selection and args are not proof. Existing architecture does not appear to have a separate tool-authorization or per-action intent proof boundary.

### Confirmation and mutations

`cancel_order` and `place_order` require a first tool invocation to yield `CONFIRMATION_REQUIRED`, then permit a retry for the same target only after `finalized_user_turn` increases (`backend/app/tools/registry.py:147-159`). The prompt tells Aria to ask for specific confirmation and retry only after clear yes (`backend/app/live/prompt.py:16-21`). This is deterministic same-session/same-target/later-turn gating, not semantic validation that the later utterance was affirmative or specific; model decides to retry. It can be unsafe if the model misreads a later unrelated turn as consent. It also leaves pending confirmation state in a map until session ends and has no explicit timeout or invalidation on changed target/context. Contract acknowledges that it does not prove what user said (`docs/ws-event-contract.md:135-139`).

Cancellation rechecks status under service lock and changes only per-session in-memory overlay; it is not a real order transaction (`backend/app/domain/orders.py:66-79`; requirements `docs/aura_skincare_functional_requirements.md:191-197`). Order placement has confirmation at tool dispatch and creates a demo order from a session cart, with idempotence per cart (`backend/app/domain/orders.py:172-191`). Neither action contacts fulfillment/payment systems.

### Product, inventory, cart, pricing, and order creation

There is a read-only cached catalog with five products, each containing only ID, name and integer INR price (`backend/app/data/products.py:16-40`; `backend/app/data/products.json:1-7`). **No stock quantity, availability, variants, SKU lifecycle, reservations, or inventory service exists.** A product being present in the JSON means catalog presence only, not in-stock status.

Cart tool accepts 1–10 distinct products, quantity 1–10, payment method COD/PREPAID. Server normalizes ID/name, rejects unknown/ambiguous match, computes line totals, shipping and COD eligibility from server-owned price (`backend/app/domain/orders.py:139-170`; contract `docs/cart-order-tool-contract.md:7-25`). Shipping boundary is <= ₹499 fee ₹50, >₹499 free; COD is <=₹2,500 (`backend/app/domain/policy.py:44-48, 118-121`). Place order rechecks COD, is cart-session-bound/idempotent, and creates Processing demo record (`orders.py:172-191`).

These are implemented demo capabilities, not reliable commerce: cart contents/prices are only in process memory; IDs restart/collide across service instances; no address, tax, stock, shipping promise, payment capture, customer ownership, inventory reservation, database transaction, concurrent checkout consistency, or external order system. The cart contract explicitly disclaims checkout/payment/account/order-system integrations (`docs/cart-order-tool-contract.md:3-5, 27-28`). Adding inventory changes cart building and placement semantics: availability must be authoritative, quantities must be rechecked/reserved atomically at placement, and failures/races must not create an order or charge. Adding accounts changes data ownership, order listing, session binding, privacy, access control, and tool arguments; model-provided customer names/IDs cannot authenticate.

### Tests and provider verification boundary

Deterministic tests cover fixtures, policies, validation, per-service isolation, confirmation turn guards, cart totals/COD, ambiguous normalized catalog names, idempotent placement, and WS lifecycle with fake live sessions (`backend/tests/test_orders.py`; `backend/tests/test_order_service.py`; `backend/tests/test_tool_registry.py`; `backend/tests/test_live.py`, including fake sessions at `:35-60`). They establish Python behavior, not Gemini’s ability to choose tools, resolve references, recognize affirmative confirmation, or speak naturally. Real smoke scripts exist but are quota-consuming (`docs/ws-event-contract.md:153-165`); none were run for this audit.

## Risks and decisions before implementation

1. **Identity/authorization:** The approved direction is a demo identity, not real authentication: the user enters a name, and the backend creates a temporary identity that authorizes access to account-mode data. The name is a label, not a credential. The implementation must bind authorization to an opaque server-issued session credential, not to the name, order number, product mention, or Gemini memory. This is not suitable for real customer data or deployment as secure authentication.
2. **Ownership/privacy:** Which order fields can be disclosed before authentication? What is the policy for account access, account recovery, unauthorized order ID, and enumeration/rate limits? Current origin restriction is not authentication (`backend/app/main.py:52-59`).
3. **Conversation context:** Approved direction is temporary browser-tab session scope across multiple voice calls, not just one WebSocket call. Retain only structured references/state needed for continuity (e.g. recently discussed order/product, pending action, cart); do not retain a full transcript or inferred personal profile across calls. The server-issued session identity and context are held in JSON-compatible process-memory state; credentials are rejected after 30 minutes without an authorized account-mode `start_call`, and process restart clears all state. Closing a tab removes its `sessionStorage` credential but does not notify the server; abandoned records are removed lazily during create/authorize operations. Define sensitive fields excluded from model context and isolation across reconnects, users, concurrent sessions, workers, and restarts. Process-local memory does not work across multiple workers without additional routing/state design.
4. **Reference resolution:** Define candidate set (only the authenticated user’s orders), aliases/product matching, recency meaning of “current,” duplicate same-product orders, cancelled/fulfilled handling, confidence threshold, and clarification behavior. Backend should return candidates/ambiguity deterministically; no guessed action target.
5. **Consent:** User accepts the MVP risk that Gemini interprets broader natural spoken confirmation. Bind a short-lived pending action to the temporary session identity, exact action, exact order/cart, quoted consequences/price, and latest fresh customer turn. Gemini's interpretation must be an explicit clear affirmative; ambiguous/negative/unrelated turns fail closed. Backend enforces session, pending-action identity, exact target/details, freshness, expiry, and one-time use; a model tool call alone is never sufficient. Semantic interpretation remains probabilistic, not deterministic proof of consent, and that risk must be explicit.
6. **Inventory:** User chose per-demo-identity inventory isolation and unlimited demo stock: each identity has its own inventory access/state, cart, and created orders; stock is not depleted in the MVP, and one identity cannot affect another. All identities use the same baseline demo catalog. Since stock is unlimited, depletion/reservation is out of MVP scope; product availability still must be backend-owned and catalog presence must not imply unsupported product claims.
7. **Commerce:** Address capture/validation and privacy, tax/shipping, price currency/version, payment collection/provider (if any), order persistence/idempotency, cancellation/refund capabilities, and failure/retry semantics. Existing demo does not settle these.
8. **Deployment architecture:** In-memory session state is process-local. Decide persistence and concurrency strategy only when requirements demand it; do not assume current in-memory state works across workers/restarts.
9. **Frontend contract coordination:** The landing page should preserve the existing Mock DB path and add a path to create a named demo identity. The backend now exposes `POST /api/demo-sessions`; the frontend contract is to keep the returned opaque credential in tab `sessionStorage`, and include it with `mode: "account"` in `start_call`. This is demo authorization only. Frontend implementation is still pending coordinated frontend work. Account commerce is currently deliberately blocked in account mode until later approved slices add account-owned operations.

## Recommended staged path (approval required per slice)

The temporary-session foundation slice is approved and complete. Remaining stages below require their own review and approval. Keep real authentication, production accounts, payment, and durable storage out of scope.

### Stage 0A — Temporary identity authorization foundation (approved slice, complete)

Implemented `POST /api/demo-sessions` with a trimmed display name and a random opaque credential returned with `Cache-Control: no-store`; only the credential digest is stored. The account-mode WebSocket start message validates that credential before Gemini connection. Existing `start_call` messages without a mode continue to use Mock DB. Existing Mock DB tools cannot be reached from account mode; until account tools are implemented they return `ACCOUNT_FEATURES_NOT_READY`. Identity credentials have a configurable sliding idle timeout (30-minute default), are refreshed by an authorized account-mode `start_call`, and are lazily pruned on session create/authorization. Process restart clears all identities. HTTP CORS is limited to configured origins and does not enable credentialed cookies.

**Acceptance/results:** valid identity creation, normalization, no-store response, digest-only credential storage, 30-minute idle expiry, allowed/denied CORS preflight, missing/invalid credential rejection before Live factory invocation, account-mode isolation from mock order lookup, and legacy Mock DB start were tested with fakes. Frontend integration is not implemented. This is a bearer-token demo authorization mechanism, not real authentication. The public creation endpoint has no rate limiting; CORS is not access control, so consider abuse limits before public deployment.

### Stage 0 — Bounded trust model contract (approved)

Define the two-mode demo contract: (a) preserve the existing Mock DB flow and its fixtures; (b) add a named, temporary demo identity whose session is authorized for its own account data, inventory access, cart, and created orders. The temporary account/session works across calls in a browser tab; the browser holds a random opaque credential in `sessionStorage`, and backend authorization expires after 30 minutes idle or restart clears state. Closing a tab removes its client-held credential; backend cleanup of the record is lazy until a later create/authorization operation. The name is only a display label. Account-mode stock is unlimited in the MVP. Retain only structured cross-call context. For Mock DB cross-call context, issue a separate anonymous mode-bound context token; legacy Mock DB calls without that token retain per-call context. Gemini may interpret spoken confirmation, but the backend must bind it to a fresh turn and exact pending action and fail closed on ambiguity; document that interpretation is probabilistic. Do not treat existing sample customer names as accounts.

**Acceptance:** a written approved contract states who may see which orders; session/auth scope and expiry; permitted memory; ambiguity and consent rules; whether any operation is only simulated. No code/provider claims.

### Stage 1 — Cross-call context, order listing, and natural-reference resolution (approved slice, complete)

Preserve existing Mock DB fixtures and behavior. User approved listing all three static Mock DB records as sample demo orders, explicitly not personal orders. Implemented `list_orders` and `resolve_order_reference` over mode-authorized candidates: Mock DB mode uses the full fixture set; account mode reads only that identity's orders (currently empty until account placement exists). Results are matched/ambiguous/not_found/needs_clarification; no guess or mutation occurs on unresolved references. Persist only a structured `last_order_id` within account identity context and an anonymous Mock DB context session. Mock context IDs authorize continuity only, are mode-bound, and are not customer authentication. Legacy Mock DB calls remain supported with per-call context. No transcript or personal profile is persisted. Source evidence: `backend/app/main.py:90-94, 276-324, 472-505`; `backend/app/domain/demo_sessions.py:52-109`; `backend/app/domain/order_resolution.py:34-98`; `backend/app/domain/orders.py:66-75`; `backend/app/tools/registry.py:168-202`.

**Acceptance/results:** Mock listing returns the three fixture records with a demo-data notice; account listing never exposes fixtures; natural “vit C” resolves ORD-101 only when unique; duplicate matches produce clarification candidates and no action; vague “that one” resolves only from scoped structured context; unknown/underspecified references do not guess; context survives calls with the corresponding session token; cross-mode token use is rejected; legacy no-token Mock DB flow remains compatible. Fake-provider tests verify backend behavior, not Gemini's natural reference/tool selection.

### Stage 2 — Action-bound confirmation for existing Mock DB mutations

Implemented a single pending-action record per call, bound to the exact mutation, canonical target arguments, order/cart detail snapshot, and finalized user turn. The initial `cancel_order` or `place_order` call without `confirmation_id` only stages the operation and returns a one-time opaque ID. Aria asks for confirmation and retries the same mutation with that ID only after Gemini interprets the immediately next finalized customer turn as a clear affirmative. The backend rejects same-turn, later/stale, expired, mismatched, changed-detail, and replay attempts; it consumes the confirmation once and the order service rechecks business policy. A new mutation supersedes prior pending consent. The default expiry is configurable at `PENDING_ACTION_TTL_SECONDS=300`.

**Accepted residual risk:** Python enforces binding, freshness, expiry, and policy but does not semantically classify speech. Gemini's interpretation of “yes” is probabilistic; the backend cannot prove the user actually consented. The model must fail closed on ambiguous/negative/unrelated turns. This accepted demo risk is not suitable as proof of consent in a real commerce system.

**Acceptance/results:** fake-session and unit tests verify no mutation on initial request, immediate-next-turn success, exact target/details binding, stale/expired/replayed rejection, single use, order/cart policy rechecks, and per-WebSocket isolation. No real Gemini call was made.

### Stage 3 — Account-owned order state and operations

Extend the completed temporary identity foundation with identity-owned orders and account operations. Tool calls derive account ownership from the authorized session, never model arguments. Keep the existing Mock DB mode and fixtures separate and unchanged. Share safe context and confirmation behavior across modes while keeping data access mode-scoped. This is demo authorization, not verified identity or real authentication.

**Acceptance:** no account-mode operation without a valid session credential; one demo identity cannot list, resolve, inspect, or mutate another identity’s data even with guessed IDs; Mock DB mode cannot access temporary account data; concurrent browser sessions are isolated; identity survives multiple calls but is cleared on server restart/reset; authorization is enforced for every account-mode tool.

### Stage 4 — Account-mode inventory, cart, and simulated order boundary

Add account-mode inventory access/state per authorized demo identity; do not alter the existing mock-order database. Each identity uses the same baseline demo catalog with unlimited stock in the MVP; inventory/order/cart state remains scoped to that identity and cannot be accessed from Mock DB mode. Keep carts and newly created orders temporary and scoped to the authorized demo identity/session. Recheck backend prices at placement; payment and durable checkout remain out of scope unless separately approved.

**Acceptance:** catalog availability is backend-owned; account identities cannot access each other's inventory/cart/orders; price/total is recomputed server-side and confirmed before placement; idempotent retry creates one order; ownership enforced; no sensitive payment data sent to Gemini. Stock is unlimited in this MVP, so depletion/oversell scenarios are not applicable.

### Stage 5 — Conversation/provider quality evaluation (separate, explicitly bounded approval)

Use deterministic fake-provider tests for event and tool protocol. If real model behavior must be assessed, obtain separate explicit permission and a precise run limit; use synthetic scenarios only and report count. Do not equate mocks with provider verification.

**Acceptance:** fake tests cover natural-reference candidate outcomes, clarification, interruption, tool denial, confirmation interruption/replay, cleanup and no leakage; any real-provider results identify exact runs and remain observational rather than authorization proof.
